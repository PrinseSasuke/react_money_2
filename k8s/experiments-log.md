# Baseline self-healing — журнал экспериментов

Дата: 2026-09-15
Кластер: k3s v1.36.4+k3s1, 1 нода (control-plane), Ubuntu 20.04.6 LTS, cgroup v2.
Метод измерения: `kubectl delete pod <имя>`, время от момента удаления до появления
**нового** пода (новое имя для Deployment, новый UID для StatefulSet) в состоянии
`Running` + `Ready=true`. Скрипт: `mttr_test.sh` (учитывает readiness/liveness пробы
из манифестов — под считается восстановленным, когда прошёл readinessProbe).

## Эксперимент 1 — backend (Deployment, 3 реплики)

- Убитый под: `backend-8fd64c8cc-lqbzb`
- Новый под: `backend-8fd64c8cc-rcm8x`
- **MTTR: 6.10 сек**
- Комментарий: во время удаления оставались 2 живые реплики backend, то есть
  сервис не имел простоя (0 downtime) — HTTP-трафик продолжал обрабатываться
  оставшимися подами, пока ReplicaSet поднимал замену.

## Эксперимент 2 — postgres (StatefulSet, 1 реплика, PVC 1Gi)

- Убитый под: `postgres-0` (пересоздаётся с тем же именем, новый UID)
- **MTTR: 7.56 сек**
- Комментарий: единственная реплика — во время пересоздания backend отвечал
  ошибками на запросы к БД (ожидаемый downtime ~7.5 сек для этого сервиса,
  в отличие от backend с 3 репликами).
- **Проверка сохранности данных:** после восстановления пода выполнен `POST
  /api/auth/login` тестового пользователя (создан до эксперимента) —
  авторизация прошла успешно, вернулся тот же `user.id`
  (`1df2fe04-336d-4021-b3b1-b34b64b0c1b2`). Данные не потеряны — PVC
  (`postgres-data-postgres-0`, hostPath-провижининг k3s local-path-provisioner)
  пережил пересоздание пода.

## Наблюдение из первого деплоя (незапланированный, но показательный кейс)

Сразу после `kubectl apply` все 3 пода backend несколько раз перезапустились
(`CrashLoopBackOff`, exit code 1) — race condition: backend стартовал
одновременно с postgres и `migrate.js` не мог законнектиться к ещё не готовой
БД. Kubernetes сам перезапускал контейнеры по `restartPolicy: Always`, пока
postgres не стал доступен — через ~25 сек все поды вышли в `Running/Ready`
без вмешательства человека. Это фактически первый живой пример self-healing
в кластере, ещё до постановки Chaos Mesh экспериментов.

**Вывод для диплома:** в текущей конфигурации нет `initContainer`/dependency-
gate между backend и postgres — приложение полагается на собственные ретраи
подключения к БД внутри контейнера и на restartPolicy Kubernetes. Это рабочий,
но не самый быстрый способ достижения консистентного старта; в разделе про
дальнейшие улучшения можно предложить `initContainer` с `pg_isready`-ожиданием
как более быстрый и предсказуемый вариант, и сравнить MTTR "холодного старта"
с этим экспериментом.
