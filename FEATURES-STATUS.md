# Статус новых фич

Обновлено: 2026-09-16. Все 5 фаз реализованы и запушены в `main` отдельными коммитами (см. историю от `Phase 1: Accounts...` до `Phase 5: Telegram bot...`).

## 1. Счета (Accounts) — ✅ готово

- Таблица `accounts`, `account_id` на `transactions`, дефолтный счёт "Основной" при регистрации, идемпотентный бэкфилл для существующих пользователей в `migrate.js` (проверено на 3 реальных локальных пользователях — сработал чисто).
- CRUD `/api/accounts`, баланс считается как `initial_balance + доход - расход`. Удаление счёта блокируется, если это последний счёт пользователя, либо требует `reassignTo` при наличии транзакций.
- Фронт: страница `/accounts`, выбор счёта в модалке транзакции, баланс по счетам на главной.

## 2. Мультивалютность (курс ЦБ РФ) — ✅ готово

- `backend/src/services/exchangeRates.js` тянет `USD`/`EUR` с `cbr.ru/scripts/XML_daily.asp`, кэширует в `exchange_rates`, обновляется кроном раз в сутки (6:00) + один раз при старте.
- `GET /api/exchange-rates`. Общий баланс на главной считается в рублях на фронте (сумма баланса каждого счёта × курс его валюты).
- Проверено вживую с реальным курсом ЦБ (100 USD + 4970 RUB → 13393.62 RUB итого).

## 3. Повторяющиеся транзакции — ✅ готово

- Таблица `recurring_transactions`, `is_auto_generated` на `transactions`. CRUD `/api/recurring`, крон-раннер (`recurringRunner.js`) раз в сутки создаёт due-транзакции и сдвигает `next_run_date`.
- Фронт: страница `/recurring` (создание/изменение/отключение/удаление), бейдж 🔁 на автосозданных транзакциях.
- Проверено: созданный ежемесячный шаблон + ручной запуск раннера → транзакция появилась, `next_run_date` сдвинулся на месяц.

## 4. Экспорт (PDF/Excel) — ✅ готово

- `GET /api/export/excel` (через `xlsx`) и `GET /api/export/pdf` (через `pdfkit`, с шрифтом DejaVu Sans для кириллицы — установлен в Dockerfile через `apk add ttf-dejavu`).
- Кнопки "Экспорт в Excel/PDF" на странице статистики, используют уже существующий выбор диапазона дат.
- Проверено: оба файла скачаны напрямую (curl + JWT), PDF содержит корректный кириллический текст, xlsx открывается с правильными кириллическими заголовками и данными.

## 5. Telegram-бот — ⚠️ частично (код готов, живое тестирование не проведено)

**Что сделано и работает:**
- Таблицы: `telegram_chat_id`, `telegram_link_code`, `last_limit_notified_month` на `users`.
- `POST /api/telegram/link-code` — генерация одноразового кода, привязка на странице "Лимит" ("Привязать Telegram" → показывает код и инструкцию).
- `backend/src/services/telegramBot.js` — обработка `/link КОД` и произвольных текстовых сообщений вида "500 такси" / "продукты 1200" (парсер числа+описания юнит-протестирован на всех примерах из ТЗ, включая нераспознаваемый текст — бот не создаёт транзакцию вслепую).
- `backend/src/services/limitAlert.js` — общая проверка превышения лимита с антиспам-защитой (`last_limit_notified_month`), переиспользуется и в боте, и при обычном создании расхода через сайт. Логика проверена: подстановка `telegram_chat_id` напрямую в БД + расход сверх лимита корректно выставили `last_limit_notified_month` один раз.
- Backend корректно стартует и мигрирует БД **без** `TELEGRAM_BOT_TOKEN` — бот просто не запускается (проверено локально), библиотека `node-telegram-bot-api` подключается лениво только при наличии токена.

**Что осталось — ручной шаг пользователя:**
- Токена `TELEGRAM_BOT_TOKEN` ещё нет. Нужно:
  1. Создать бота через `@BotFather` в Telegram, получить токен.
  2. Добавить `TELEGRAM_BOT_TOKEN=<токен>` в `.env` на проде (рядом с `JWT_SECRET`) и передеплоить (`docker compose up -d --build backend`, либо просто рестарт контейнера, если `.env` уже обновлён — `docker-compose.yml` уже прокидывает переменную).
  3. После этого протестировать вживую: `/link КОД` из настроек лимита, отправку "500 такси" и проверку уведомления о превышении лимита.
- Без этого шага фича не может быть протестирована end-to-end с реальным Telegram — весь код к этому готов и не блокирует остальной функционал.

## Сборка

Перед каждым коммитом: `npm run build` (фронт) — зелёный на всех 5 фазах. Backend проверялся через `docker compose up -d --build postgres backend` + чтение логов миграции локально (Docker Desktop на этой машине); каждая фаза добавляла свои `ALTER TABLE ... ADD COLUMN IF NOT EXISTS` / `CREATE TABLE IF NOT EXISTS` в `backend/migrations/init.sql`, все прогонялись идемпотентно на уже существующей локальной базе без ошибок.
