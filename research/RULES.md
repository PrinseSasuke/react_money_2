# Правила разработки — трек `research/ids-ml`

Обязательны к соблюдению при разработке подсистемы генерации датасета и сравнения
детекторов. Главная цель правил — **полная изоляция от основной дипломной работы**
и **безопасность изолированного стенда**.

---

## 1. Изоляция от диплома (жёстко)

1. **Отдельная ветка.** Вся работа ведётся в `research/ids-ml`, ответвлённой от
   `main`. В `main` этот трек не мёржится до отдельного решения. Создание:
   ```bash
   git checkout -b research/ids-ml
   ```
2. **Только каталог `research/`.** Разрешено создавать/менять файлы **только**
   внутри `research/`. Файлы `backend/`, `frontend/`, `k8s/`, `scripts/` и
   `scripts/chaos_run.py` — **read-only**. Нарушение = откат.
3. **Никакого импорта из диплома.** Нельзя `import` из `scripts/` в код `research/`
   (это создаёт связанность). Нужное (например словарь серий) **копируется** в
   `research/` с комментарием-ссылкой на первоисточник и датой копии.
4. **Проверка изоляции — в каждом коммите.** Перед коммитом:
   ```bash
   git diff --stat main -- ':!research' | grep . && echo "НАРУШЕНИЕ: тронуты файлы вне research/" || echo "OK: изоляция цела"
   ```
   Если что-то показано — вынести изменение обратно в `research/` или откатить.
5. **Общие namespace'ы — только на чтение.** `react-money`, `monitoring`,
   `loadtest` читаются (состояние, метрики, переиспользование нагрузки), но их
   **манифесты не редактируются**. Приложение — неизменная мишень.
6. **Свои namespace'ы для записи.** Всё, что трек создаёт в кластере (атакующие
   Job'ы, sink, NetworkPolicy), живёт в ns `redlab`.

---

## 2. Безопасность стенда (авторизованное исследование)

1. **Только свой стенд, только своё приложение.** Любой сценарий направлен
   исключительно на `react-money` в собственном k3s. Внешние адреса, чужие хосты,
   публичные сервисы — **запрещены** в конфигурации сценариев и в коде.
2. **Egress закрыт.** ns `redlab` обязан иметь `NetworkPolicy`, запрещающую любой
   выход в интернет (разрешены только `react-money`, внутренний sink, DNS).
   `labctl doctor` проверяет её наличие и **блокирует** запуск атак при отсутствии.
3. **Готовые инструменты, не самописные эксплойты.** Атаки исполняются признанными
   тулзами (Chaos Mesh, Stratus Red Team, sqlmap, hydra/patator, k6, iperf3),
   запускаемыми как параметризованные Job'ы. Цель — **наблюдаемый след в метриках**,
   не получение доступа/данных.
4. **Никаких реальных секретов.** Тестовый пользователь, токены, словари для
   brute-force — синтетические, из Secret/ConfigMap в `redlab`. Реальные учётные
   данные в сценарии не попадают.
5. **Жёсткие лимиты и таймауты.** Каждый атакующий под — с `resources.limits` и
   `activeDeadlineSeconds`; криптоджекинг-профиль ограничен по CPU/mem, чтобы не
   уронить узел.
6. **Есть аварийный стоп.** `labctl scenario stop` полностью и идемпотентно
   очищает стенд (Job'ы `redlab`, Chaos-объекты, k6). Реализуется до первой атаки.
7. **Данные эксфильтрации никуда не уходят.** Sink — внутренний, принятый объём
   отбрасывается; наружу ничего не передаётся и не сохраняется.

## 3. Git-workflow

1. Ветка `research/ids-ml`; допускаются подветки `research/ids-ml/<фича>`.
2. Атомарные коммиты по этапам M0–M5 (см. `TZ.md` §7).
3. Формат сообщения коммита:
   ```
   research(ids-ml): <краткое действие>

   <что и зачем, если неочевидно>

   Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>
   ```
4. Перед коммитом — прогнать проверку изоляции из §1.4.
5. `research/results/` и `research/dataset.csv` — крупные/производные артефакты:
   в `research/.gitignore` игнорировать сырые выгрузки и картинки, версионировать
   только `report.md`, `metrics.json`, `versions.txt`, `config.json`.
6. `journal.jsonl` — **версионируется** (это первичная разметка, ценность для
   воспроизводимости).

## 4. Код

1. **Оркестратор — Python 3, stdlib-only** на стороне сервера (как
   `chaos_run.py`: `argparse, csv, json, math, urllib, subprocess, yaml`). Никаких
   pip-зависимостей на k3s-узле.
2. **ML-часть — отдельный модуль** (`research/ml/`), запускается на машине с
   pandas/numpy/scikit-learn; зависимости фиксируются в
   `research/ml/requirements.txt`. На узле кластера не выполняется.
3. **Стиль — как в проекте.** Русские шапки-комментарии у сценариев (заголовок,
   ATT&CK, инструмент, ожидаемый след, гипотеза). Русские сообщения лога с иконкой
   и временем, как в `chaos_run.py` (`log("✅", "...")`).
4. **Kubernetes — через `kubectl` subprocess** (как в `chaos_run.py`), одинаковая
   функция-обёртка с проверкой кода возврата.
5. **Идемпотентность и cleanup.** Любой запуск можно прервать; `finally` пишет
   `end_ts` в журнал и не оставляет висящих объектов сверх ожидаемых.
6. **Детерминизм разметки.** Разметка полностью выводится из `journal.jsonl`;
   `dataset build` воспроизводим (R-10).
7. **Никаких сетевых вызовов наружу из кода** трека (кроме обращения к локальному
   Prometheus и kube-API).

---

## 5. Документирование для статьи

1. Каждый прогон фиксирует версии инструментов и образов в
   `research/results/<ts>/versions.txt`.
2. `THREAT-MODEL.md` держать в актуальном состоянии: сценарий ↔ техника ATT&CK ↔
   инструмент ↔ ожидаемый след. Это таблица методики для статьи.
3. Результаты и выводы — в `report.md` этапа M4/M5; честно фиксировать
   ограничения (дисбаланс классов, cAdvisor latency, недоступные экспортёры) — как
   это уже сделано в `k8s/anomaly-detection/STATUS.md`.

---

## 6. Определение готовности (Definition of Done)

Задача этапа считается выполненной, когда:
- соответствующие критерии приёмки `TZ.md` §6 выполнены;
- проверка изоляции §1.4 чистая;
- `labctl doctor` зелёный;
- изменения только в `research/`, коммит оформлен по §3.
