# Техническое задание

## Подсистема генерации размеченного датасета и сравнения ML-детекторов атак по метрикам мониторинга Kubernetes

Версия 1.0 · трек `research/ids-ml` · изолирован от основной дипломной работы

---

## 1. Назначение и цель

### 1.1. Проблема

Классические детекторы аномалий по метрикам инфраструктуры не различают **причину**
аномалии. Всплеск latency, рост ошибок или насыщение CPU может быть вызван как
**штатным сбоем** (деградация сети до БД, падение пода, пик легитимной нагрузки),
так и **атакой** (перебор паролей, флуд на API, SQL-инъекции, криптоджекинг,
эксфильтрация). Детектор, обученный только на «норма vs аномалия», даёт высокую
долю ложных тревог на обычных сбоях, что делает его непригодным для SOC.

### 1.2. Цель

Разработать воспроизводимый стенд, который **автоматически** генерирует
размеченный временной ряд метрик с тремя классами — **норма / сбой / атака** — и
на нём экспериментально сравнить детекторы, способные **отличать атаку от сбоя**,
а не только находить отклонение от нормы.

### 1.3. Научная новизна (для статьи)

- Единая методика генерации данных, где каждый класс порождается **признанным
  инструментом своего домена**: норма — k6, сбой — Chaos Mesh (CNCF), атака —
  Stratus Red Team / профильные утилиты, с привязкой к **MITRE ATT&CK for
  Containers**.
- Автоматическая разметка по временным окнам запусков — без ручной аннотации.
- Явная метрика качества **«доля ложных тревог на сбоях»** (false-attack rate),
  которой нет в работах по детекции аномалий «норма vs аномалия».

### 1.4. Что НЕ входит в задачу

- Реальная эксплуатация уязвимостей ради получения доступа/данных — не требуется;
  нужен только **наблюдаемый след в метриках**.
- Изменение основного приложения `react-money`, его манифестов или пайплайна.
- Продуктивное развёртывание детектора (только оффлайн-эксперимент для статьи).

## 2. Границы и изоляция от дипломной работы

Требование заказчика: исследовательский трек **не должен затрагивать** основную
дипломную работу.

| Аспект | Основная работа | Этот трек |
|---|---|---|
| Git-ветка | `main` | `research/ids-ml` (см. `RULES.md`) |
| Каталог | `backend/`, `frontend/`, `k8s/`, `scripts/chaos_run.py` | только `research/` |
| Namespace приложения | `react-money` (**общий, только цель атак — не меняется**) | — |
| Namespace нагрузки | `loadtest` | переиспользуется как источник «нормы» |
| Namespace сбоев | Chaos Mesh в `react-money` | переиспользуется как источник «сбоя» |
| Namespace атак | — | **новый `redlab`** (изолированный, egress закрыт) |
| Namespace приёмника эксфильтрации | — | **новый `redlab`** (внутренний sink) |
| Результаты | `scripts/results/` | `research/results/` |
| Мониторинг | `monitoring` (Prometheus) | переиспользуется на чтение |

**Правило:** трек **читает** из существующих namespace'ов (Prometheus, состояние
приложения) и **пишет** только в свои `research/` и `redlab`. Ни один файл вне
`research/` не редактируется. Приложение `react-money` выступает мишенью в
неизменном виде — это часть чистоты эксперимента.

## 3. Архитектура

```
                       ┌─────────────────────────────────────────┐
                       │              k3s cluster                  │
                       │                                           │
  research/ (host) ──► │  ns loadtest   ── k6 ──► ┌────────────┐   │
  ┌──────────────┐     │  ns react-money(Chaos)─► │ react-money│   │
  │   labctl     │     │  ns redlab   ── attack ─►│  (target)  │   │
  │ (оркестратор)│     │                          └─────┬──────┘   │
  └──────┬───────┘     │  ns redlab   ◄─ exfil ─────────┘          │
         │             │  ns monitoring (Prometheus) ◄─ scrape all │
         │  read       │                                           │
         └─────────────┼──────────────────────────────────────────┘
                       │
   journal.jsonl ◄─────┘  (метки: класс, техника, start_ts, end_ts, интенсивность)
         │
         ▼
   dataset.csv (окна метрик + метка) ──► feature build ──► ML train/eval ──► report
```

### 3.1. Поток данных

1. `labctl scenario run <name>` запускает **фон нормы** (k6) + целевой сценарий
   (сбой Chaos Mesh **или** атаку через Job/Stratus), фиксирует `start_ts` и
   `end_ts`, дописывает строку в `journal.jsonl`.
2. `labctl dataset build` выгружает из Prometheus временной ряд по всем сериям
   метрик за период всех прогонов, нарезает на окна, размечает каждое окно по
   `journal.jsonl`, пишет `dataset.csv`.
3. `labctl model train` строит признаки, обучает и сравнивает детекторы, пишет
   метрики качества и графики в `research/results/`.

## 4. Компоненты и требования

### 4.1. `labctl` — оркестратор (CLI)

Единая точка входа, стилистически повторяет существующий `scripts/chaos_run.py`
(argparse, русские сообщения, лог с иконками и временем, tmux-обёртка для
устойчивости к обрыву SSH). Пишется на Python 3, **stdlib-only** на стороне
сервера (как `chaos_run.py`: `csv`, `json`, `math`, `urllib`, `subprocess`,
`yaml`). Тяжёлые ML-зависимости — только на этапе `model train`, который
выполняется на машине с ресурсами (см. 4.5), не на k3s-узле.

Подкоманды:

| Команда | Поведение |
|---|---|
| `labctl doctor` | Проверка изоляции: существуют ns `redlab`; NetworkPolicy egress-deny применена; Prometheus доступен; целевые сервисы `react-money` живы; ветка git = `research/ids-ml`. Без этого прогоны не запускаются. |
| `labctl scenario list` | Список сценариев из `research/scenarios/` (класс, техника ATT&CK, длительность). |
| `labctl scenario run <name>` | Один сценарий: `нагрузка → baseline(3 мин) → сценарий → recovery → запись метки`. |
| `labctl scenario run all` | Все сценарии по порядку с cooldown между ними (по образцу `chaos run all`). |
| `labctl scenario status` | Что запущено сейчас (Job'ы в `redlab`, Chaos-объекты, k6). |
| `labctl scenario stop` | Аварийная остановка: удалить все Job'ы `redlab`, Chaos-объекты, k6-нагрузку. |
| `labctl dataset build` | Собрать `dataset.csv` из Prometheus по `journal.jsonl`. |
| `labctl model train` | Обучить и сравнить детекторы, выгрузить отчёт. |

Требования:
- **R-1.** Каждый прогон обязан записать в `journal.jsonl` строку со схемой §5.1,
  даже при аварийном завершении (запись `end_ts` в `finally`).
- **R-2.** Перед запуском атаки `labctl` обязан проверить `doctor`-инварианты
  изоляции; при провале — отказ с понятным сообщением, без запуска.
- **R-3.** Все атакующие Job'ы создаются **только** в ns `redlab` с
  `activeDeadlineSeconds` (жёсткий таймаут) и `ttlSecondsAfterFinished`.
- **R-4.** `labctl scenario stop` должен полностью очищать стенд до состояния
  «только норма/ничего» — идемпотентно.

### 4.2. Каталог сценариев `research/scenarios/`

Каждый сценарий — либо Chaos Mesh CRD (класс «сбой»), либо манифест Job с готовым
инструментом (класс «атака»), с русской шапкой-комментарием в стиле
`k8s/chaos/experiments/`:

```
# <NN> · <класс> · <название>: <короткое описание>.
# ATT&CK: <Txxxx> (<название техники>)          # только для атак
# Инструмент: <tool>
# Ожидаемый след: <какие серии метрик и как отклонятся>
# Гипотеза: <что должно произойти>
```

Файлы называются `NN-<class>-<slug>.yaml`, где `class ∈ {norm, fault, attack}`.

Стартовый набор сценариев (детально — в `THREAT-MODEL.md`):

| NN | Класс | Сценарий | Инструмент | ATT&CK |
|---|---|---|---|---|
| 00 | norm | Эталонная нагрузка 100 rps | k6 (`k8s/load`) | — |
| 10 | fault | Задержка backend→postgres 300ms | Chaos Mesh NetworkChaos | — |
| 11 | fault | Kill backend | Chaos Mesh PodChaos | — |
| 12 | fault | CPU-стресс backend | Chaos Mesh StressChaos | — |
| 20 | attack | Перебор паролей на `/api/auth/login` | Job: hydra/patator | T1110 |
| 21 | attack | Флуд-DDoS на API | Job: k6 агрессивный профиль | T1499 |
| 22 | attack | Сканирование SQLi по API | Job: sqlmap | T1190 |
| 23 | attack | Криптоджекинг-профиль (CPU/mem) | Chaos Mesh StressChaos / stress-ng | T1496 |
| 24 | attack | Эксфильтрация: объёмный egress на внутренний sink | Job: iperf3/curl → sink в `redlab` | T1048 |

> Расширяемо: движок `Stratus Red Team` подключается как альтернативный
> исполнитель для техник, которые он покрывает; веб-специфика (login/SQLi) — через
> Job'ы с профильными утилитами.

Требования:
- **R-5.** Атакующие сценарии не содержат жёстко зашитых учётных данных/токенов;
  тестовый пользователь и словарь берутся из Secret/ConfigMap в `redlab`.
- **R-6.** Интенсивность (rate, число потоков, длительность) параметризуется через
  env, чтобы можно было варьировать «силу» для устойчивости датасета.

### 4.3. Изоляция стенда (обязательные k8s-объекты)

- **R-7.** ns `redlab` с `NetworkPolicy`:
  - egress: разрешён только к сервисам `react-money` и к внутреннему sink в
    `redlab`, DNS (kube-dns). **Любой выход в интернет запрещён.**
  - ingress: закрыт извне.
- **R-8.** Все атакующие поды — с `resources.limits` (CPU/mem), чтобы не положить
  узел (особенно криптоджекинг-профиль).
- **R-9.** Sink эксфильтрации (`iperf3 -s` или netcat-приёмник) — Deployment в
  `redlab`, данные никуда не сохраняются и не покидают кластер.

### 4.4. Сбор и разметка датасета

`labctl dataset build`:
- Переиспользует словарь серий метрик из `chaos_run.py` (`SERIES`) как основу и
  расширяет специфичными для атак сериями (см. §5.2). **Импортировать нельзя без
  нарушения изоляции**, поэтому создаётся собственная копия `research/series.py`
  с комментарием-ссылкой на оригинал (правило «не трогаем файлы диплома»).
- Выгружает `query_range` по каждой серии за `[min(start)-buffer, max(end)+buffer]`
  с шагом `step` (по умолчанию 10 с — из опыта STATUS.md, где `[40s]@step=10s`
  дал плотные данные).
- Нарезает на скользящие окна длиной `W` (по умолчанию 30 с) с шагом `S`
  (по умолчанию 10 с).
- Каждому окну присваивает метку по перекрытию с интервалами `journal.jsonl`:
  окно относится к классу, чей интервал покрывает центр окна; при отсутствии
  перекрытия — `norm`. Переходные окна (частичное перекрытие) помечаются флагом
  `boundary=1` и по умолчанию исключаются из train (настраивается).

Требования:
- **R-10.** Разметка **детерминирована** и полностью восстановима из
  `journal.jsonl` — повторный `dataset build` даёт идентичный CSV.
- **R-11.** В CSV сохраняются `window_start`, `window_end`, `class`, `technique`,
  `scenario`, `boundary`, все признаки (§5.2).

### 4.5. ML-эксперимент `labctl model train`

Выполняется на машине с pandas/numpy/scikit-learn (не на k3s-узле). Детекторы для
сравнения:

| Модель | Тип | Роль |
|---|---|---|
| Пороговые правила (baseline) | эвристика | имитация Alertmanager: флаг при превышении порогов |
| Isolation Forest | unsupervised | «норма vs аномалия», не различает причину |
| One-Class SVM | unsupervised | то же, для сравнения |
| Random Forest | supervised, 3 класса | норма / сбой / атака |
| XGBoost / Gradient Boosting | supervised, 3 класса | норма / сбой / атака |
| (опц.) LSTM-автоэнкодер | unsupervised | по последовательности окон |

Метрики качества:
- Precision / Recall / F1 по каждому классу (macro и weighted).
- **False-attack rate** — доля окон класса «сбой», ошибочно помеченных «атакой»
  (ключевая метрика новизны).
- **Задержка обнаружения** (detection latency) — как в STATUS.md, время от начала
  события до первого верного флага.
- Матрица ошибок (3×3).

Требования:
- **R-12.** Разбиение train/test — **по прогонам, а не по окнам** (окна одного
  прогона не должны попадать и в train, и в test — иначе утечка).
- **R-13.** Все результаты, конфиги и версии инструментов фиксируются в
  `research/results/<timestamp>/` для воспроизводимости в статье.
- **R-14.** Отчёт включает таблицы метрик, матрицы ошибок, графики временных рядов
  с наложенными интервалами событий и флагами детекторов.

## 5. Форматы данных

### 5.1. `research/journal.jsonl` (журнал прогонов, одна строка = один запуск)

```json
{
  "run_id": "2026-09-25T14-03-11_20-attack-bruteforce",
  "scenario": "20-attack-bruteforce",
  "class": "attack",
  "technique": "T1110",
  "tool": "hydra",
  "intensity": {"threads": 16, "rate": null},
  "baseline_start": 1758801791.0,
  "start_ts": 1758801971.0,
  "end_ts": 1758802271.0,
  "recovery_end": 1758802451.0,
  "target": "react-money/backend:/api/auth/login",
  "notes": ""
}
```

### 5.2. `research/dataset.csv` (колонки)

Служебные: `window_start, window_end, run_id, scenario, class, technique, boundary`.

Признаки (окно агрегируется в: mean, max, p95, slope — по каждой серии):
- Из существующего `SERIES`: `rps_total, rps_4xx, rps_5xx, err_pct, lat_mean_s,
  lat_p95_s, open_conns, cpu_cores, cpu_pct_req, mem_bytes, hpa_replicas,
  restarts, pg_up, pg_tps, pg_active`.
- Специфичные для атак (добавить в `research/series.py`):
  - `rps_401_403` — доля 401/403 на `/api/auth/*` (сигнатура brute-force).
  - `rps_login` — RPS именно на `/login`.
  - `net_tx_bytes` / `net_rx_bytes` по подам (сигнатура эксфильтрации/флуда).
  - `req_p99_s` — хвост latency (флуд/SQLi).
  - `pg_errors` / `pg_rollbacks` — рост при SQLi (если экспортируется).
  - `unique_src_ratio` — при наличии, разнообразие источников (флуд).

### 5.3. `research/results/<timestamp>/`

`config.json` (параметры прогона), `metrics.json` (все числа), `confusion_*.png`,
`timeseries_*.png`, `report.md`, `versions.txt` (версии инструментов и образов).

## 6. Критерии приёмки

- **A-1.** `labctl doctor` проходит; при удалённой NetworkPolicy — падает и
  блокирует запуск атак.
- **A-2.** `labctl scenario run all` выполняет весь набор (≥2 сбоя, ≥4 атаки,
  норма) без ручного вмешательства и полностью очищает стенд после.
- **A-3.** `journal.jsonl` содержит корректные интервалы для каждого прогона;
  повторный `dataset build` даёт побитово идентичный `dataset.csv` (R-10).
- **A-4.** `dataset.csv` содержит все три класса, число окон каждого класса
  достаточно для обучения (порог задаётся, напр. ≥200 окон/класс суммарно по
  прогонам).
- **A-5.** `model train` выдаёт отчёт со всеми метриками §4.5, включая
  false-attack rate и матрицы ошибок; supervised-модель различает «сбой» и
  «атаку» заметно лучше unsupervised-baseline (это и есть результат статьи).
- **A-6.** Ни один файл вне `research/` не изменён (проверка `git diff --stat`
  относительно `main` по путям).
- **A-7.** Ни один атакующий под не имеет egress в интернет (проверяется тестом:
  под в `redlab` не может достучаться до внешнего адреса).

## 8. Риски и допущения

- **Ограниченные ресурсы k3s-узла** (из STATUS.md: нет pip, нет pandas). →
  Оркестратор — stdlib-only; ML — на отдельной машине по выгруженному CSV.
- **Частота обновления cAdvisor ~10–20 с** ограничивает detection latency снизу.
  → Шаг/окно ≥10 с; интерпретировать latency с этой поправкой (как в STATUS.md).
- **Дисбаланс классов** (нормы много, атак мало). → Множественные прогоны атак с
  разной интенсивностью; при обучении — class weights / стратификация по прогонам.
- **Экспортёр Postgres может не отдавать pg_errors/rollbacks.** → Проверить на M3;
  при отсутствии — исключить эти признаки, зафиксировать в ограничениях статьи.
- **Stratus Red Team может не покрывать веб-специфику.** → login/SQLi остаются на
  профильных утилитах в Job'ах; Stratus — для техник, которые он поддерживает.
